# Teams — parallel work, organised by feature system

The project is split by **feature system**, not by app. Each system is
one independent module with one team, one public interface, and its own
tests — so teams build in parallel without stepping on each other. The
host and student apps are thin shells that plug the systems together.
The maintainer (Vikram) reviews every PR and owns the contracts.

## The feature systems

| # | System | Module | What it does | Used by |
|---|---|---|---|---|
| 1 | QR | `android/features/qr/` | Generate QR (host) + scan QR (student) | Host app, student app |
| 2 | Bluetooth | `android/features/ble/` | Advertise token (host) + scan + RSSI (student) | Host app, student app |
| 3 | Permissions | `android/features/permissions/` | All runtime permission flows: ask, explain, denied → settings | Every feature that needs a permission |
| 4 | FRS | `android/features/frs/` | Face recognition at login — verifies the person is the student (contract §7) | Student app (login gate) |
| 5 | Token | `rust/token-core/` (+ Kotlin `TokenRotator`) | HMAC token generation + verification, 30s windows | Host app, server, laptop beacon |
| 6 | Server | `server/session-api/`, `server/verification/`, `server/attendance-store/` | Sessions, verification, records | Host app, student app |
| 7 | App shells | `android/host-app/`, `android/student-app/` | Screens + wiring the systems together | — (they compose the rest) |

A junior joins **one** system. Systems do not edit each other's folders —
if you need a change in another system's module, open an issue and tag
that system instead of reaching across.

## The rules that make parallel work real

1. **A system is a module with an interface.** Other code uses the
   system only through its public interface (the functions listed in
   the module's README). Nobody reaches into another system's internals.
   If the interface is missing something you need, propose the addition
   in an issue — do not work around it.
2. **A system builds and tests alone.** Each module has its own tests
   and can be compiled without the apps. If your module only works when
   the whole app runs, it is not finished.
3. **Stubs, not waiting.** No system waits for another to be done:
   - The student shell does not wait for the server — it runs against a
     stub API that always answers `{"status": "present"}` for a
     well-formed request (contract §5). Swap the base URL when the real
     server lands.
   - The QR scanner team does not wait for the host app — it tests
     against a printed QR, or a QR generated by the QR system's own
     generator.
   - The BLE scanner team does not wait for the host app — it tests
     against the laptop beacon (`devtools/laptop-beacon/`).
   - The permissions system does not wait for anyone — its flows are
     testable with any permission.
   A stub is allowed to be dumb. It is not allowed to disagree with the
   contract in `docs/CONTRACTS.md`.
4. **Permissions live in one place.** No feature asks for permissions
   directly — every request goes through the permissions system, so
   there is exactly one place where "denied / don't ask again / go to
   settings" is handled, and it behaves the same in both apps.

## Moving the existing code into systems

The host starter was written before this split, so its code still lives
in one package. Moving it is part of the work, one tracked move per
system — not a big-bang rewrite:

| Current location | Moves to | Notes |
|---|---|---|
| `QrCode.kt` | `features/qr/` | Generator side; scanner is new work |
| `BleAdvertiser.kt` | `features/ble/` | Advertiser side; scanner is new work |
| Permission code in `MainActivity.kt` | `features/permissions/` | Becomes the shared permission flow |
| `TokenRotator.kt` | stays, mirrored by `rust/token-core/` | Token contract §1 is the spec for both |

Each move is its own issue and its own PR. The app must still compile
and run after each move — move, wire up, test, merge, then the next one.

## Integration rhythm

- **Weekly integration:** once a week (maintainer picks the day), every
  system merges to `main` and someone runs the end-to-end check: host
  starts a session → student scans + submits → record appears in the
  attendance list. What is not integrated yet is listed honestly in the
  repo README status section.
- **Contract changes:** only by PR to `docs/CONTRACTS.md`, maintainer
  approved, with a message to all teams. If you build against an old
  contract, your PR will fail review — read that file before coding.
- **One issue, one person, one PR** — same as `CONTRIBUTING.md`. A team
  of 3 works on 3 different issues, not one giant shared branch.

## How a new junior joins

1. Read `README.md`, `docs/ARCHITECTURE.md`, and `docs/CONTRACTS.md`.
2. Pick a system (or ask the maintainer which system needs people).
3. Take a `good first issue` in that system's folder.
4. Follow `CONTRIBUTING.md` — fork, branch, PR, review.

## What "parallel infrastructure" means here — and what it does not

- It means: independent feature modules, each owned by one team, each
  testable alone, plugged together through written interfaces and
  contracts. Any system can be rebuilt or replaced without touching the
  others.
- It does **not** mean Kubernetes, service meshes, or message queues.
  At 50–70 phones in a room, that machinery would slow the juniors down
  and teach them tooling instead of building. The module boundaries in
  this doc are where a bigger split would happen if it is ever needed —
  the design already points that way, it just does not pay the cost yet.
